# Invitations and Members

Relay has no accounts. An invitation link **is** the account. This document
describes the model, the token rules, the member cookie, and the operations the
host and members can perform.

The current implementation lives in [`internal/serve/keys.go`](../internal/serve/keys.go),
[`internal/serve/invites.go`](../internal/serve/invites.go), and
[`internal/serve/session.go`](../internal/serve/session.go). Display names, the
member cookie, and the welcome page are built (Phase 1 of
[`pivot-plan.md`](pivot-plan.md)).

## The model in one picture

```
HOST
 └─ invite ──► ALICE ──► invite ──► BOB ──► invite ──► CAROL
                  │
                  └─ invite ──► DANA

revoke ALICE  =  ALICE + BOB + CAROL + DANA lose their keys
revoke BOB    =  BOB + CAROL lose their keys
```

- The host creates the first invitations from the operator console.
- Any live member can create an invitation for someone else.
- The new member is labelled with the inviter's name and the new name:
  `alice/bob`. This is a display label, not a path.
- Revoking a key revokes every key below it in the invitation tree.
- Rotating a key issues a fresh token for the same member. The rest of the tree
  stays attached.

A member is a person or a small group sharing one link. "Friendgroup" accounts
work because one invitation can be used by several people; there is no device
limit and no per-person identity. If that is not wanted, invite one person per
link.

## Why invitation links instead of accounts

- **Nothing to remember.** The link is the credential.
- **Nothing to recover.** There is no email, password, or security question to
  lose.
- **The group grows by vouching.** A member can only invite people they choose.
- **Revocation is a tree operation.** Removing one person removes the people
  they brought in, unless the host re-invites them.

The cost is real: anyone who has the link is the member, and losing the link
means asking the host to rotate. Treat invitation links like passwords.

## Token format

A token is 32 random bytes from `crypto/rand`, encoded as unpadded base64url
(43 characters). The node stores:

- the plaintext token, so the operator console can reveal and copy it;
- a SHA-256 hash, used for constant-time authentication.

The plaintext-at-rest choice is a convenience for the host. A later phase should
store only the hash and rely on rotation for lost links. Until then, protect the
data directory like a password store.

Tokens appear only:

- in the invitation link fragment (`#key=…`), which browsers do not send to the
  server;
- in the `Authorization: Bearer …` header for API and CLI use;
- in the operator console, after an explicit reveal;
- in the member cookie after the session exchange.

Never put a token in a query string, a path, a log line, or a commit.

## Invitation link

Current shape:

```
https://relay.example.org/_relay/home.html#key=<token>
```

The home page reads the fragment, exchanges it for a cookie, and shows the
member welcome screen:

1. The page reads the fragment in the browser.
2. It POSTs the token to `/_relay/v1/session`.
3. The node verifies the token, sets a member cookie, and answers with the
   member view.
4. The page strips the fragment from the address bar and shows the home.

Existing links that point at `/_relay/publish.html#key=<token>` keep working:
the publish page performs the same exchange, hides the key field, and can still
publish immediately. New links generated by the host console point at the home.

The fragment is never sent in the initial HTTP request. The token travels once,
in the POST body, over TLS.

## The member cookie

| Attribute | Value |
|---|---|
| Name | `relay_member` |
| Value | the invitation token |
| `HttpOnly` | yes |
| `SameSite` | `Lax` |
| `Secure` | yes when the node serves HTTPS |
| `Path` | `/` |
| Lifetime | 30 days |

The server authenticates the cookie exactly like a bearer token: hash it, look
it up, check that the key is live. Revocation takes effect on the next request.
There is no separate session table to expire. Signing out clears the cookie but
does not revoke the key.

CSRF protection is same-origin checks on every mutating request:

- require `Origin` or `Referer` to match the node when present;
- require `Content-Type: application/json` for JSON endpoints;
- never accept a mutating `GET`;
- keep `SameSite=Lax`.

The cookie is the browser identity. The bearer token remains valid for the CLI
and AI assistants. Both are the same credential, and both work on the deploy
and invite endpoints; a signed-in browser does not need to paste the key again.

## Member record

Today a key record is:

```json
{
  "id": "dk_…",
  "user": "alice/bob",
  "token": "…",
  "hash": "…",
  "created": "2026-10-19T12:00:00Z",
  "revoked": false,
  "invitedBy": "dk_…"
}
```

The pivot adds:

```json
{
  "displayName": "Bob",
  "bio": "Runs the Thursday reading group.",
  "joinedAt": "2026-10-19T12:00:00Z"
}
```

`user` stays as the stable label and the fallback display name. `id` is the
member id used by posts and comments. `displayName` and `bio` are editable by
the member (Phase 1/2) and by the host.

## Operations

### Host: create an invitation

1. Open `/_relay/admin.html` and sign in with the admin token.
2. Enter a name (letters, digits, `.`, `_`, `-`; up to 63 characters).
3. Create the key.
4. Copy the invitation link and send it over a channel the recipient trusts.
5. Do not email it in plain text if you can avoid it.

The admin console can also reveal the current token for a key. Treat that view
as a secret.

### Member: invite someone

1. Open the publish page while signed in.
2. Enter the new person's name.
3. Copy the new invitation link and send it. It opens the new member's home.

The new key appears under the inviter as `inviter/name`. The inviter cannot
revoke someone above them, and cannot see the admin console.

### Host: revoke

Revoking a key:

- stops authentication immediately for that token and cookie;
- stops every key in its invitation subtree;
- does not delete posts or comments by default.

Revocation is idempotent: revoking an already-revoked key is not an error.
A confirmation view of the subtree is Phase 5.

### Host: rotate

Rotating:

- issues a new token for the same member and key id;
- invalidates the old token and cookie;
- keeps the invitation subtree attached;
- keeps the member's posts and comments.

Use rotation when a link leaks or a member gets a new device and cannot find the
old link.

### Member: sign out

Signing out clears the cookie. It does not revoke the key. The member can sign
back in with the invitation link or by pasting the token.

## Limits and abuse

- Default member ceiling: 29 by design. A `--max-members` flag and its
  enforcement are Phase 5.
- Invitation creation is rate-limited per member (Phase 5).
- An invitation can have an optional expiry (Phase 5). Default: never.
- A revoked branch cannot invite.
- The host can always revoke the root of a branch.

There is no public sign-up, no password reset, and no way to discover a node's
invitations from outside.

## What is not solved yet

- Hashed-only tokens (no plaintext at rest).
- Per-device sessions and "sign out everywhere".
- Invitation expiry UI.
- A member-visible list of who invited whom.
- Transferring a node to a new host without invalidating every link.

These are tracked in [`pivot-plan.md`](pivot-plan.md) §7 and Phase 5.
